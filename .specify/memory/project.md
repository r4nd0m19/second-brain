## 0. 愿景与核心能力（用户初稿，2026-10-01）

**一句话愿景**：把用户的数字生活（文件、浏览记录、ChatGPT 对话、与 AI 的对话）统一沉淀成可对话的第二大脑 —— 提供像 ChatGPT 一样的体验，但回答基于你自己的全部数据。

**核心能力**：
- **数据来源（4 类）**：
  1. 用户上传的各种形式文件（书籍、文档等）
  2. 浏览器数据
  3. ChatGPT 对话数据
  4. 用户与第二大脑自身的对话
- **对话体验**：像 ChatGPT 一样的问答界面
- **模型接入**：外接 GPT / DeepSeek 等模型 API（2026-10-01 决定：不采用"接入 ChatGPT 账号"—— 非官方途径、不稳定且有合规风险；v1 走 API key）
- **检索与兜底**：优先从个人数据库中检索作答；库中没有的问题用外接模型回答，并**将对话回写数据库**（数据自增长闭环）
- **主动洞察（远期）**：分析个人数据，主动给出建设性建议（如：发现你在学 SDD → 推荐优质学习资源；或指出更值得做的事）—— 见附录 D B3

**典型能力场景（用户提供，作为验收场景素材）**：
1. 回答"3 天前浏览过的 Next.js 教程"中的细节
2. 回忆"10 天前与 ChatGPT 讨论过的 Upwork 项目"的完整信息
3. 在"一年前上传的《SDD实战》"书中定位问题的答案
4. 库中无答案时用外接模型作答并记录

**已确认的关键决策（访谈 2026-10-01）**：
- 使用者：先自己用（单人）；**架构、数据模型与认证边界必须为将来多用户扩展留路**（2026-10-01 补充为选型约束；v1 不实现多用户功能）
- 隐私模型：**自有服务器集中式**（2026-10-01 细化，原"混合"）—— 所有数据（含浏览记录）统一存于自租服务器，双端一致可见可查；防护靠：不进第三方 SaaS + TLS/磁盘加密 + 采集黑名单 + 删除权。不做本地孤岛（本地-only 数据 = 另一端问不到）
- 双端需求：**Windows 电脑 + Android 手机都要能用**
- 双端方案：**租服务器路线** —— 大脑（应用 + 数据库 + 检索）跑在自租服务器（国内轻量 ~¥100/年 或 Hetzner ~¥30/月），Windows 与 Android 均作为客户端访问
- 客户端形态：**PWA** —— 浏览器访问，可"安装"到 Windows 与 Android，形似原生应用
- 采集范围：**双端全自动采集**（2026-10-01 决策）—— Windows：Chrome/Edge 扩展；Android：Firefox 安卓 + 扩展（前提：手机浏览改用 Firefox；扩展手动更新）
- 分期构建：F1 核心问答 → F2 Windows 采集 → F3 Android 采集（先后顺序，不是砍范围）
- **已交付增强（2026-10-02）**：MCP 接入 —— Claude Code 等 agent harness 经 `/mcp` 检索/回存第二大脑（独立 feature：`specs/003-mcp-access/`；超出 F1–F3 路线图的首个 harness 集成）
- **已交付增强（2026-10-02）**：联网检索（库外兜底，F4）—— 本地库无相关内容时可联网搜索作答（智谱 Web Search；未配 key 静默关闭；成本护栏 30 次/天）：`specs/004-web-search/`（真实 key 核验 + quickstart 全量演练通过；显式联网指令 FR-011 与裸指令引导式回应同日增补——用户反馈驱动）
- v1 数据源：上传文件 + 浏览器数据 + 与第二大脑的对话（ChatGPT 历史暂缓）

**仍开放**：技术栈（留待 plan 阶段对比）；采集黑名单的具体站点/类别（spec/plan 阶段细化）

**采集可行性**：已调研确认 —— 浏览器正文采集与 ChatGPT 对话采集（回填 + 增量）均有成熟路径，见附录 C。

## 1. 立项背景

<!-- 草稿，2026-10-01；如有修正随时改 -->
- 个人数字生活规模持续增长：浏览的网页、与 AI 的对话、文件资料分散在各自孤岛
- 通用 AI（ChatGPT 等）能力强但没有个人上下文，每次都要从零解释背景
- 平台数据锁定：ChatGPT 对话导出链路繁琐，数据在平台侧，不可自由检索
- 时机：2026 年外部模型 API（GPT/DeepSeek 等）与 RAG 技术成熟、成本极低（个人月成本约几元），自建"个人 AI 记忆"第一次经济可行

## 2. 目标用户

<!-- 草稿，2026-10-01；如有修正随时改 -->
- 核心用户：作者本人（单人使用，Windows 电脑 + Android 手机双端）
- 用户角色：唯一用户（同时也是开发者）—— 日常浏览/阅读/对话后，需要随时找回信息的人
- 典型使用场景：
  1. 浏览教程/文档后，数天后询问其中的细节
  2. 回忆与 ChatGPT 讨论过的项目信息（v1 暂缓，见 Non-Goals）
  3. 上传书籍/文档后，基于内容提问
  4. 遇到库外问题，由外部模型回答并沉淀回库

## 3. Problem Statement

<!-- 草稿，2026-10-01；如有修正随时改 -->
- 用户当前怎么解决：依赖浏览器历史、ChatGPT 侧边栏搜索、文件夹翻找，基本靠记忆
- 当前方案的低效点：检索弱（浏览器历史只能搜标题/URL）、无上下文（通用 AI 不知道你看过什么）、数据分散在多个平台
- 最大痛点：看过 / 聊过 / 存过的信息，过几周后基本找不回来
- 本项目范围内要解决：把个人数字生活统一入库，提供对话式检索与兜底回答（v1 范围：上传文件 + 浏览器数据 + 自身对话）

## 4. Goals（可验证）

<!-- 草稿，2026-10-01；如有修正随时改 -->
- [ ] G1：上传的文件（中/英文）能用自然语言问出细节，回答能定位到原文出处
- [ ] G2：≥3 天前浏览过的网页内容，可通过对话找回（以"3 天前看过的 Next.js 教程"为验收案例）
- [ ] G3：与"第二大脑"的历史对话能被后续提问引用（数据闭环基础）
- [ ] G4：库外问题由外部模型兜底回答并自动入库；同一问题第二次问可直接命中库

## 5. Non-Goals（明确不做）

<!-- 草稿，2026-10-01；如有修正随时改 -->
- 多用户功能（账号体系 / 协作 / 计费）—— v1 不实现；但架构、数据模型与认证边界需为多用户留路（见 §0 决策）
- ChatGPT 历史导入 —— 暂缓（路径已明确，见附录 C，但不在 v1）
- 原生 App —— 用 PWA 代替
- 本地大模型 —— v1 全部走外部 API
- 全平台采集 —— 手机端仅覆盖 Firefox 浏览器内浏览；Chrome 安卓 / App 内置浏览器（如微信）内的浏览采集不到

## 6. 非功能需求（项目级底线）

<!-- 草稿，2026-10-01；如有修正随时改；feature 级细化在各自 spec.md 的 NFR 节 -->

### 6.1 Performance
- 检索命中的提问：10 秒内开始流式回复
- 数据量到 10 万条仍可用（检索不显著降级）

### 6.2 Reliability
- 已入库数据不丢：定期备份 / 可导出
- 服务器故障后可恢复（数据可重建索引）

### 6.3 Security
- 仅本人可访问：强认证 + HTTPS
- API Key 与个人数据最小暴露（自租服务器，不用第三方 SaaS）
- 数据可控：可删除任意单条入库内容、可按时间范围清理（如某段浏览记录）；删除在备份中同步生效

### 6.4 Scalability
- 按单人规模设计；架构保留多用户余地，但不为其增加 v1 复杂度

## 7. 总体用户旅程（User Flow 总览）

<!-- 草稿，2026-10-01；如有修正随时改；具体交互细节由各 feature 的 spec.md 承载 -->

> 日常采集（浏览扩展 / 上传文件 / 对话）→ 沉淀入库 → 两端随时提问 → 命中：带出处的回答 / 未命中：外部模型兜底回答 → 兜底内容自动入库 → 下次命中

## 8. 技术栈与理由

**已确认约束（访谈）**：大脑部署在自租服务器；客户端为 PWA（Windows + Android）；模型能力来自外部 API（GPT/DeepSeek 等）；基础设施预算：服务器 ~¥100–400/年量级，模型 API 按量计费（个人用量约每月几元）。**选型已于 2026-10-01 定稿（详见 `specs/001-core-qa/plan.md`）**：

| 层次 | 选择 | 理由 | 备选及放弃原因 |
|------|------|------|----------------|
| 总体路线 | 自研（组件搭建） | spec 定制行为多、代码可控 | 二开 Khoj/AnythingLLM（定制冲突 + 许可/维护） |
| 后端 | Python 3.12 + FastAPI | RAG 生态最强（Docling 仅 Python） | 纯 TS（解析生态弱） |
| 前端 | Next.js 静态导出（PWA） | 体验 + 单进程托管、运维最简 | Vite+React（可随时换）；双服务（升级路径） |
| 数据库/检索 | Postgres 16 + pgvector（+FTS） | 多用户零迁移债、混合检索内建 | SQLite+sqlite-vec（迁移债）/ LanceDB |
| Embedding | 云 API（硅基流动 bge-m3 默认候选） | 省服务器资源、可扩多用户 | 本地 CPU（隐私优；接口保留可切换）；**IV 例外已登记** |
| 文档解析 | Docling（MIT） | 结构保留 + 标题路径分块 + 多格式 | PyMuPDF 等（许可/结构问题，详见 plan） |
| 部署 | 单体 FastAPI（API + 静态托管）+ Postgres；2C4G 起步 | 单人运维最简 | 双服务 + 反代（多用户/独立扩展时切换） |

## 9. 总体架构与理由（原骨架 9.2 + 10 合并）

**已确认约束（访谈）**：以服务器为中心（应用 + 数据库 + 检索），Windows/Android 通过 HTTPS 访问；采集端（浏览器扩展）→ 自建 API → 入库。

**F1 定稿（2026-10-01）**：单体 FastAPI（REST + SSE + 托管 Next.js 静态 PWA）+ Postgres/pgvector + 云 embedding + 外部对话模型；原文件磁盘存储（按归属分区）；采集端（F2 起）→ 同一 API → 入库。详见 `specs/001-core-qa/plan.md`。

**前端交互决策（2026-10-04）**：**一套代码 + 手机范式改造**（媒体查询 ≤720px，不搞两套代码/独立移动端）——对话页会话列表=左上汉堡侧滑抽屉（ChatGPT 移动端同款）、筛选/引文/预览=底部弹层、触控目标 ≥40px；依据与调研见 `specs/001-core-qa/research.md` R44，实施见 001 T030。

## 附录 C：技术调研笔记（2026-10-01）

### 浏览器内容采集（可行，模式成熟）

- 标配：Manifest V3 扩展 + Readability.js 正文提取（+ Turndown 转 Markdown）→ POST 到自建 API → 入库
- 参考先例：Hoardy-Web（被动全量捕获，"私人 Wayback Machine"）、ArchiveBox（自托管归档）、LLM Wiki Clipper / IceWhisperer（Readability → 自建端点）
- 关键设计点：访问时自动触发（非手动 clip）；敏感站点黑名单；同 URL 去重/更新
- 现实约束：Chrome Android 无扩展支持（2026 确认；Kiwi 已停维）
- 手机端采集决策（2026-10-01）：**全自动路径 = Firefox 安卓 + 自研扩展**（AMO unlisted 签名 → .xpi 传手机 → 设置 → 关于 Firefox → 点 logo 5 次 → Install Extension from File）；代价：手机浏览改用 Firefox、扩展无自动更新
  - 备选（plan 阶段研究）：Chromium 系安卓浏览器（Vivaldi/Quetta 可装 Chrome Web Store 扩展）→ 扩展私有发布到 CWS，若可行可免换浏览器
  - 补充候选：PWA Share Target（分享存档）—— 可覆盖"App 内分享"场景（参考 EasyDrop）

### ChatGPT 对话采集（两条腿）

- 回填：官方 Settings → Data controls → Export data → 邮件 ZIP（链接 24h 过期），内含 `conversations.json`（完整消息树/时间戳/模型；大导出拆分为多文件）
- 增量：扩展在 chatgpt.com 监听会话数据（网络响应拦截优于 DOM 刮取）→ 推送自建 API；先例：MemoryPlugin（扩展后台同步）、multi-ai-exporter（定时+增量导出）
- 风险：OpenAI 改版会打断采集器 → 做成独立可维护模块，失效不影响核心问答
